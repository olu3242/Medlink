# Runtime Evidence Repository

The evidence repository stores artifacts generated by certified runtime
components. It does not evaluate compliance, block deployments, or generate
operational evidence.

## Lifecycle and integrity

Evidence is appended as an immutable record. Canonically ordered content and the
version number are hashed with SHA-256. Verification recomputes the hash. A new
version references its parent and receives a new identifier; prior versions are
never overwritten.

Metadata must contain operational facts only. Do not store payloads, credentials,
SQL, stack traces, patient information, or unredacted log messages.

## Retention

Configurable classes are `temporary`, `operational`, `audit`, `compliance`, and
`permanent`. Retention calculates archive or expiration eligibility without
mutating stored evidence. Physical archival and cleanup are deployment concerns.

## Providers

Runtime modules implement `EvidenceProvider` and register with
`EvidenceCollector`. Providers return already-produced evidence; collectors do
not infer or manufacture compliance results.

## Administrative APIs

- `/runtime/evidence`
- `/runtime/evidence/{id}`
- `/runtime/evidence/search`
- `/runtime/evidence/categories`

Search supports type, category, time range, correlation ID, and certification
profile. All endpoints require platform or tenant administrator authorization and
disable caching.

The administrative APIs use `SupabaseEvidenceStore`, backed by the append-only
`runtime_evidence_records` table with tenant-aware RLS. `MemoryEvidenceStore` is
reserved for isolated tests.
